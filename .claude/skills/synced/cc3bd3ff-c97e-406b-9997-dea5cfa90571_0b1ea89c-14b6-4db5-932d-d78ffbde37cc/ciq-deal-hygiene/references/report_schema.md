# Report schema — your daily hygiene report (Google Drive)

Your report is a **Google Doc** in your **CIQ Hygiene Reports** Drive folder, titled
`Hygiene Report — <Your Name> — <YYYY-MM-DD>`. You arrive at it via the **link in your Slack DM** or by
opening the **newest** Doc in that folder. The Doc is structured as: a **headline** (score, deal counts);
**per-deal cards sorted worst-first**, each containing flags, recommended next step + due date, MEDDPICC
gaps + how-to-fix, win-with competitive angle, evidence citations, resolver findings, and a HubSpot link;
a **trailing clean-deal list** for a quick "still current?" check; and (since 2026-07-11) a final
**`MACHINE-READABLE DATA (JSON)` appendix** carrying the exact engine record the Doc was rendered from.
This skill **reads** this Doc — it does not recompute it.

**Parse the appendix as the authoritative record.** The JSON wrapper is
`{schema: "ciq-hygiene-report/v1", report_date, flags_as_of, owner, rep, headline: {score, total,
need_updates, clean}, score_formula, since_last, shown, recommendations: [...]}` — `recommendations[]`
entries are documented below. Two wrapper blocks added in v4.6 (absent in older Docs — handle gracefully):
- `score_formula` — the rep-level score inputs: `{score, cleanliness (of 80), cadence (of 20),
  coverage_pct, wo (offense weight), cap (capacity), worked, n}`. Use these exact numbers when the rep asks
  "why is my score X" — never re-derive.
- `since_last` — movement vs the previous run: `{prev_as_of, cleared: [{deal, kinds, left_scope?}],
  new: [{deal, kinds}], persisting_worked: [{deal, kinds}]}`. Open the walk with this (wins first);
  `persisting_worked` = the rep touched the deal but a flag's clear-condition isn't met yet.
Take deal ids, flags, values, dates, and evidence from the JSON; the prose cards are its rendering, and
where they differ the JSON wins. The Doc also opens with a **FOR CLAUDE** instruction block — it is part of
the contract and restates this skill's rules for any AI that reaches the Doc without the skill loaded.
Docs published before 2026-07-11 have no appendix — read the prose cards as before.

The Doc is generated by RevOps' `publish_rep_reports.py` from the same engine that produces the scorecard — it is exactly what you are scored on.

## Top level
The fields of the engine record (= the appendix JSON's `recommendations` context):
| Field | Meaning |
|---|---|
| `owner` | your HubSpot owner id |
| `rep` | your name |
| `flags_as_of` | the date the flags/scorecard were computed (tell the rep this) |
| `count` | number of deals in `recommendations` |
| `recommendations` | array of per-deal entries, **pre-sorted worst-first** (critical-flagged first, then by priority) |

## Per-deal entry (`recommendations[]`)
| Field | Meaning / how to use it |
|---|---|
| `deal_id` | HubSpot deal id — use for the fresh-read before writing |
| `dealname` | deal name |
| `hubspot_url` | direct link — show it to the rep |
| `arr` | net-new ARR (USD) |
| `close` | close date (YYYY-MM-DD) |
| `fcat` | forecast category (COMMIT / BEST_CASE / OMIT) |
| `hygiene_flags` | the live flags, e.g. `"CRIT dark 133d"`, `"WARN thin MEDDPICC"`, `"CRIT close-date/stage incoherent"`. **Empty = clean** (just confirm the next step). These are exactly what the scorecard shows — do not re-derive them. |
| `score_math` | *(v4.6, may be null on older data)* the deal's score transparency block: `{score (0–100), wo (offense weight), worked (bool — materially edited in the cadence window), flags: [{k, sev, age, pts, why, clear}]}`. `pts` = the flag's actual score contribution (CRITICAL 5 / WARNING 2, ×2 when age ≥7d; `onhold` = 0). **`clear` is the fix target** — propose changes that meet it. `worked=true` + flags = "your edit registered but doesn't meet the clear condition." Never recompute any of these. |
| `meddpicc_gaps` | which MEDDPICC elements are thin (friendly labels: Pain, Metrics, Decision Criteria, Decision Process, Paper Process) |
| `meddpicc_fix` | per-gap **how-to-write-it guidance** + a good example. Use it to draft/confirm the field text to the right depth. |
| `next_step` | the recommended next move (one action, named person) — propose this as the appended Next Step |
| `due_date` | a realistic by-when for the next step (≥ today) |
| `reach_out_to` | who to contact (name + role) |
| `channel` | email / call / meeting / exec_sponsor / in_person |
| `win_with` | the competitive angle (one line) — context for the rep, not a write |
| `evidence` | what the recommendation is grounded in, in **readable** terms (email **subject** / meeting **title** + date). Cite this when proposing a change. |
| `priority` | high / medium / low (deterministic) |
| `resolver` | body-verified, **recommend-only** findings (high/medium confidence), or absent. See below. |
| `n_emails`, `n_meetings` | how much engagement context the engine had |
| `log_meeting` | *(optional)* object `{"note_date": "YYYY-MM-DD", "note_excerpt": "…"}` — present when the engine found a recent onsite/meeting recorded only as a HubSpot Note engagement (not a Meeting). The Doc renders this as a **📝 Log the Meeting** card line instructing the rep to convert it to a proper Meeting engagement with date, participants, and outcome. Null or absent = no action needed. |
| `multithread` | *(optional)* object `{"single_threaded": true/false, "known_contacts": ["Name", …]}` — present when the deal appears dark and single-threaded after pricing discussions. The Doc renders this as a **🧵 Multi-thread** card line instructing the rep to identify another stakeholder (e.g. an exec above the buyer) or trigger a marketing nurture sequence rather than re-emailing the same contact. `known_contacts` lists the contacts the engine already sees on the deal. Null or absent = no action needed. |
| `resolver_pending` | *(optional, boolean)* — `true` when this deal is classified as a channel/partner deal (C2) but has not yet had a resolver pass to scope its engagement bundle to the correct end customer. The Doc renders a **⚠ Channel deal — verify scope** note advising the rep that the recommendation may include content from a sibling deal the shared partner also works, and to keep the recommendation scoped to this deal's own end customer. Absent or `false` = no note rendered. Team-level partner-spanning warnings (a partner working multiple open deals with **distinct** end customers) are surfaced by the **manager skill** via `scorecard_data.sibling_deal_warnings`, not here. |

## `resolver` block (when present)
Body-verified findings from RevOps' engagement resolver — **recommend-only**, surfaced for the rep to act on:
| Field | Meaning |
|---|---|
| `confidence` | high / medium |
| `is_channel` | true if a reseller/distributor is involved |
| `notes[]` | one or more of: **body-verified last contact `<date>`** (catches a "dark" flag that's actually alive via the reseller — log that contact on the deal); **true end customer may be `<X>` (CRM tag: wrong)** — **surface only**: the rep fixes the End-Customer association in the **HubSpot UI**, or the daily batch's association audit handles it. This is **NOT** a rep-skill write (company-association labels EC 78 / Reseller 3 / Distributor 80 are out of scope — the connector can't read association typeIds; see SKILL.md "What this skill does NOT do"). **possible duplicate (`<relation>`)** — surface for the rep to resolve. |

## How the skill uses it
- `hygiene_flags` → what to fix per deal (already matches the scorecard).
- `next_step` + `due_date` → the appended Next Step.
- `meddpicc_gaps` + `meddpicc_fix` → which fields to fill + how; draft from the deal's emails/calls, confirm with the rep.
- `resolver.notes` → surface false-dark / EC re-tag / duplicate, recommend-only.
- `evidence` → cite when proposing each change (Principle 0).

## Planned additions (coming with the publisher — handle gracefully if absent)
Future report versions may add, per gap, a **drafted field value** (`draft`) cited to evidence, and a **`clarifying_q`** for fields with no evidence in the record. When present: show a `draft` as a DRAFT to confirm/edit; when a `clarifying_q` is present (or a gap has neither draft nor evidence), **ask the rep** for the content rather than inventing it. If these fields are absent, fall back to `meddpicc_fix` guidance + draft from the live record on confirm.
