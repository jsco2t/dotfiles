# Roster agent contract

Every roster agent (the definitions in `~/.claude/agents/`) follows this contract when it
is dispatched by the task-orchestrator. The orchestrator's brief gives the specifics; this
document gives the rules that never change.

## 1. The brief

Every dispatch prompt is a brief generated by `orch brief`. It contains:

- **Identity** — `workflow`, `stage`, and, where applicable, `task`, `attempt`, `round`,
  `loop`, `snapshot`, `plan_revision`, `plan_hash`, `scan_digest`. Echo them **exactly**
  in your result block; they pin what you evaluated.
- **Read these in full** — the decisions log first, then the task/plan documents, earlier
  stage reports, the task diff (`changes.patch`, `changed-files.txt`), the integrity scan
  (`scan.md`), and evidence logs. Read them; do not skim or rely on a summary.
- **What this stage must produce** — the stage's job. Your agent definition's matching
  *mode* section says how.
- **Finish** — your report path and the result-block template.

If the brief is missing something you need, that is a `needs_input`, not a guess.

## 2. The result block

Your **final message** must end with one fenced block, every placeholder replaced:

````
```orch-result
{
  "workflow": "2026-09-25-example",
  "stage": "review",
  "task": "T003",
  "attempt": 1,
  "round": 0,
  "snapshot": "g:8f2c…",
  "status": "complete",
  "verdict": "pass",
  "report": "/abs/path/to/workflow/runs/T003/a1/06-review-r0.code-reviewer.md",
  "findings": {"blocking": 0, "recorded": 2, "disputes_ruled": 0}
}
```
````

The SubagentStop hook parses it from your final message and appends it to the ledger with
your harness-supplied agent type. **An invalid or missing block means your work is not
recorded** and you will be resumed to fix it. Rules:

| Field | Meaning |
| --- | --- |
| `status` | `complete` — you finished the stage. `needs_input` — you cannot finish without answers (list them in `questions` and in the report). `blocked` — the plan cannot be followed as written (list `deviations`). |
| `verdict` | Gate stages (readiness, pm-*, verification, review, final-review, final-verification, plan-review): `pass` or `fail`. Work stages (work, fix, research, plan, test-plan, final-fix): `n/a`. |
| `report` | Absolute path from the brief. Its file name ends in `.<your-agent-type>.md`. |
| `criteria` | verification / final-verification: one entry per acceptance criterion id — `{"id": "AC1", "met": true, "evidence": "<concrete>"}`. `met` is a JSON boolean; evidence is never empty for a met criterion. |
| `findings` | review / final-review: integer counts. `blocking` = findings with confidence ≥ 85 that must be fixed; `recorded` = non-blocking findings; `disputes_ruled` = author disputes you ruled on. |
| `scan_digest` | pm-accept: the digest of the scan you adjudicated (from the brief). |
| `changed_files` | work / fix by authors: workspace-relative paths you changed (the PM compares this to the real diff). |
| `external_action` | liaison work: `none`, `dry-run`, or `executed`. |
| `questions`, `deviations` | Lists of strings when status is `needs_input` / `blocked`. |

Booleans are JSON `true`/`false`; counts are integers; never leave `"pass | fail"`.

## 3. Reports

- Write your full report to the brief's report path, using the Write tool. Hooks allow you
  to write **only** files whose name ends in `.<your-agent-type>.md` inside the workflow
  directory (plus, for authors, files inside the declared workspaces).
- Structure: a one-paragraph summary with the verdict first, then the substance (findings,
  evidence, criteria table, what changed), then anything the next stage must know.
- Every claim cites evidence: `path:line`, a command and its result, a test name, a URL.
- Never edit `.orch/`, plan documents after approval, generated `index.md`/`status.md`
  files, `decisions.md`, or another agent's report.

## 4. Snapshots

A snapshot id (`g:…`, `s:…`, `gs:…`) names the exact content of a workspace. Evaluate the
workspace as it is at the snapshot in your brief. If you notice the workspace changing
while you work, say so and finish with `status: blocked`. Any later change makes your
verdict stale and the orchestrator will re-dispatch — so a pass you give is a pass for
exactly what you saw.

## 5. Talking to the rest of the team

You cannot talk to the user (AskUserQuestion is unavailable to subagents) and you do not
message other agents. The orchestrator routes everything through files:

- **Need input?** Finish with `status: needs_input` and precise questions (what you need,
  why, what you would do with each possible answer). You will be **resumed** — with your
  context intact — once answered. Never guess to fill a gap.
- **Disagree with a finding?** (authors) In a fix round, mark it `disputed` with concrete
  evidence. Reviewers must rule on every dispute in their next pass: withdraw it or
  maintain it with evidence. Neither side "wins" by persistence — unresolved disputes go to
  the human when the review budget runs out.
- **The plan is wrong or impossible?** Do not work around it. Finish with `status: blocked`
  and `deviations`; the human decides.
- **Clarifications** the orchestrator or human made are in `decisions.md` and bind you.

## 6. Skills inside agents

Most specialists do their work by invoking a skill (Skill tool). Skills written for
interactive use ask questions; inside an agent:

- Pass every argument a skill would otherwise ask for (mode, scope, paths, thresholds) so
  it never needs to ask.
- When a skill reaches an interactive step ("ask what to do", "present the outline for
  approval", "which scope?", "post comments?"), **do not wait**: take the non-interactive
  choice the agent definition names (usually "write the report to a file"), or, if the
  step is a genuine decision the plan did not make, finish with `needs_input`.
- A skill's fan-out may hit the concurrent-subagent limit. If a sub-agent dispatch fails,
  re-dispatch it after others return; **never drop a review lens** — report which lenses
  ran.
- Never post to GitHub/Jira/Confluence from a review or research skill (local modes only).

## 7. Orchestrator commands you may run

Subagents may run only these `orch` commands (hook-enforced):
`status`, `evidence`, `gate run`, `wait`, `snapshot`, `task diff`, `task scan`, `task status`,
`ledger`, `validate`, `plan-hash`, `where`. Everything else (notes, starting, accepting,
failing tasks, rounds, loops, approvals) is the orchestrator's. No command may reference
`.orch/`.

```bash
ORCH='python3 "$HOME/.claude/skills/task-orchestrator/scripts/orch.py"'
```

**Long runs.** The Bash tool stops a command after 10 minutes at most. When `orch evidence` or
`orch gate run` may take longer, add `--detach`, then `$ORCH wait <job-id>` with a Bash timeout
of 600000; if the wait reports the job is still running, wait again. Never skip or narrow a
command because it is slow.

## 8. Quality gates every agent applies to itself

Before you finish, check:

1. I did everything my stage asked, for every item — no sampling, no "and so on".
2. Every claim in my report has evidence a reader can verify.
3. I did not change anything outside my role (read-only roles changed nothing; authors
   changed only in-scope files).
4. I did not weaken a test, an assertion, a criterion, or a finding to make progress.
5. My result block matches my report, uses the brief's identity values, and is valid JSON.
