# CIQ Deal Creation — rep self-serve (v1.2)

This skill helps a CIQ rep create a **complete, well-qualified, forecast-accurate** deal in HubSpot with minimal manual work — while making it impossible to create the two things that poison downstream reporting: an **unqualified deal** (no BANT) and a **deal with no valid product backing** (`hs_tcv = null`, invisible to ARR forecasting). It is **write-capable** and therefore governed by a strict confirm-before-write discipline.

**Core loop:** read corrections + reference (Phase 0) → qualify BANT (hard gate) → intake (transcript-first) → resolve company/products/contacts live in HubSpot → present ONE complete summary → get an explicit "Create the deal" → execute in order → validate the result. **Never create a deal that fails the BANT gate. Never create a line item by copying product fields — always link the product so HubSpot inherits them (see `references/line_item_creation.md`).**

## What you need connected
- **HubSpot** (required, write-capable) — to search companies/products/contacts and create the deal, line items, and associations. Writes go through `manage_crm_objects`; owner names resolve live via `search_owners`. If the connector is **read-only** (no `manage_crm_objects` loaded), you cannot create anything — say so plainly, hand back the finalized spec as a manual-entry checklist, and stop. Do **not** loop retrying a write tool that isn't present, and never show a "deal created" message for a write that didn't happen.
- **Products read access** — required to validate SKUs and pull `hs_price_{currency}`. If Products returns an authorization error, you cannot validate the SKU; flag it and get an admin to grant access or have someone with access read back the product record. Do not invent SKU/price/billing values.

## Phase 0 — Read the corrections log and reference (do this BEFORE any tool call)
1. Read `corrections_log.md` in full. It is the catalog of things prior versions got wrong (owner-ID mismaps, the line-item field-copy bug, stage-probability drift, superseded API claims). Treat it as authoritative over anything in the reference that conflicts, and over your own priors.
2. Skim `references/ciq_reference.md` for the IDs/fields you'll need. **Never hardcode an owner name, and never hardcode a stage probability** — resolve owners live from the HubSpot owners object and, for any forecasting, pull `hs_deal_stage_probability` live (creation itself doesn't use probabilities — new deals enter at Discovery).

## Asking questions — use tappable options, not walls of text
When you need the rep to make a **finite choice**, present it as **tappable multiple-choice options** (the interactive input tool) rather than making them type. Reps are usually on mobile, and tapping a button beats scrolling up to re-read a question and typing each answer — this is the exact friction that made deal creation painful before (reps re-typing choices, or accidentally pasting the question list back). Rules:
- **Tappable = finite, enumerable answers:** deal type · currency · reseller Yes/No · Professional Services Yes/No · **deal source** (Marketing / SDR / Sales / Partner Channel / Cloud BD) · product flavor & tier (e.g. Open-Source Rocky vs RLC; RLC Basic/Standard/Premium/Hardened; Ascender per-node vs ELA) · competition (from the enum) · contact role (Champion / Economic Buyer / Both / basic) · Expansion+Renewal Yes/No · "which company?" when there are multiple matches · "same opportunity or new deal?" · and the final **Create / Change / Cancel** decision. Option sets come from `references/ciq_reference.md` (§6 deal types, §7 currencies, §12 competition, §13 products, §14 deal source) and `references/deal_setup_and_naming.md` — don't retype them, pull from there.
- **Free text = names, dates, numbers, narrative:** company name · contact names + titles · close/term dates · node counts / quantities · discount intent (**capture as the rep expresses it — "X% off", "$S per unit", or "deal/ARR/TCV/ACV must be $X" — the skill converts it to per-unit later; see `references/line_item_creation.md` §Discount arithmetic**) · SKU strings · and MEDDPICC prose (Identified Pain, Metrics, Decision Process). Never force these into buttons.
- **Extract from the transcript first; only ask for genuine gaps.** Never present a choice whose answer is already in the transcript or inferable — that just adds clicks.
- **Batch up to ~3 related choices per prompt** (e.g. deal type + currency + reseller together). Each interactive prompt **ends your turn** — the rep's taps arrive as their next message; then continue. Don't keep writing after the prompt.
- **The final create-confirmation can be tappable** — "Create the deal" / "Change something" / "Cancel." A tapped **"Create the deal"** is an explicit, unambiguous confirmation and satisfies golden rule 2 (better than a typed "ok").
- **Fallback:** if the interactive tool isn't available in the rep's client, ask the same questions concisely in text (still batched, still transcript-gaps-only).

## The BANT gate — HARD STOP, no exceptions
**Do not create a deal, and do not proceed to the summary, unless all four are confirmed.** This is a hard block, not a soft warning, and it holds even when the rep insists, provides a dollar amount, or says "I'll fill the rest in myself." A missing criterion is a `❌ Cannot create deal — missing [criterion]` and a redirect to qualify. See `references/bant_and_meddpicc.md` for accept/block phrasing.
- **Budget** — allocated or identified. "Don't know / need to find out / just exploring" → BLOCK.
- **Authority** — decision-maker by **name AND title**. First-name-only or title-only → BLOCK.
- **Need** — specific pain **AND** a product match. "Interested in learning more" with no product → BLOCK.
- **Timeline** — a decision/implementation date, quarter, or compelling event. "No rush / whenever" → BLOCK.

Never create from a bare website form, a pricing-only inquiry, or a "tell me more" contact — those are not qualified opportunities.

## Phase 1 — Intake (transcript-first)
Ask once: *"Do you have a transcript, email thread, or call notes? If so, share it and I'll extract everything; if not, I'll ask BANT directly."*
- **With a transcript** → extract BANT silently, then everything else (products, contacts, dates, competition, metrics, deal source). If BANT is incomplete, show what you found, name what's missing, and STOP at the gate.
- **Without** → ask BANT first (4), then deal basics (company, close date, currency, deal source), terms (start/end), products, contacts. Use **tappable options** for the finite-choice answers (deal type, currency, reseller, deal source, product tier) and free text for names/dates/numbers/pain — see "Asking questions" above. References: `references/bant_and_meddpicc.md` and `references/deal_setup_and_naming.md`.

## Phase 2 — Resolve everything live in HubSpot (read-only calls)
1. **Company** — search with fuzzy matching ("Advance" should find "Advanced"). Multiple hits → present the matches as **tappable options** and let the rep pick; if the hits look like duplicate records of the same company, use the one the rep confirms and **flag the possible duplicate to RevOps** (the merge audit owns merges — don't merge yourself). No hit → confirm you'll create it. Use the **exact HubSpot name** for the deal name (smart-abbreviate only very long org names, e.g. "Sandia National Laboratories" → "Sandia").
2. **Existing open deals** — search the company for open deals before creating. **Define "open" by excluding the Won + closed stage IDs, not by `hs_is_closed`** (HubSpot reports `hs_is_closed = false` on the Sales Won stage `93217107` — see REF §3/§8). If a genuinely open deal exists, offer a **tappable** "same opportunity (update) / new deal / cancel." A Won/closed deal for the same company is not a reason to block a new deal — and never edit its close date.
3. **Products** — search **Active SKUs only** (`hs_status = "active"`, NOT `sku_status`). When flavor/tier is ambiguous, present the options as **tappable choices** (e.g. RLC Basic/Standard/Premium/Hardened). Pull the product record to get the real SKU, `hs_price_{deal_currency}`, class, category, and billing fields. **Validate the SKU the rep gives you against the live record** — a plausible-looking SKU string is not a validated SKU (see corrections log: the `Ascender-PRO-PRM` vs real `ASC-PRO-PRM` miss, plus a decoy inactive SKU). If the price doesn't match what the rep expects, surface the discrepancy before proceeding.
4. **Contacts** — **search before creating, then create immediately if genuinely absent.** Search each contact by name AND email AND the company's domain (a person often exists under a personal/Gmail identity from a conference scan — if a likely twin exists, use it and flag the extra email for RevOps to add as a secondary, rather than creating a duplicate). If truly not in HubSpot, create the contact now and associate it to the company (extract title/role from the transcript); do not defer to "manual steps."

## Phase 3 — Present ONE complete summary, then wait for explicit confirmation
Show the full deal in one screen: BANT ✅, deal info (including **owner** and **deal source**), terms (with auto-calculated term length), the **line-item table with product-verified values**, company associations, contact associations + MEDDPICC labels, MEDDPICC text, and Next Step. Then present the choices as **tappable options**: `Create the deal` / `Change something` / `Add line item` / `Cancel`.
- **Execute only on explicit, unambiguous confirmation** — a tapped **"Create the deal"** counts (it's explicit), as does typed "Create the deal" / "Yes, create it". Treat "ok" / "sure" / "sounds good" as NOT confirmation → re-present the tappable choices. (Offer once: "Want to skip per-write confirmations for this chat?" — if yes, proceed through the execution steps without re-confirming each, but still show the final pre-write summary.)
- If any product/SKU/price is still unvalidated, the line item is **blocked** — show the summary but do not create until it's resolved. At least one valid line item is a hard requirement; there is no "create without line items," even on request.

## Phase 4 — Execute (strict order)
Follow `references/deal_setup_and_naming.md` for property values and `references/line_item_creation.md` for the line item. All writes via `manage_crm_objects` (`confirmationStatus: "CONFIRMED"`). Order:
1. **Calculate** `length_of_term__months_` from term dates; set `ascender_se = 432367417` if any line item's product category is Ascender (⚠ see corrections log D-10 — value under RevOps review).
2. **Create the deal** (Sales → Discovery `93217102`, or Renewal → Upcoming Renewals `125777759`) with core + term + **source** (`deal_source`; `channel_created_opportunity` on reseller-originated deals) + MEDDPICC properties. **Owner:** `hubspot_owner_id` defaults to the creating rep (resolved live); if the rep is creating on someone else's behalf, confirm the intended owner explicitly. Include the Primary company association in the create call.
3. **Add the End Customer association** (label name **"End Customer"**) — required on **every** deal, via a `manage_crm_objects` update on the deal with `associations: [{targetObjectId: <company_id>, targetObjectType: "companies", labels: ["End Customer"]}]`. Direct deal: same company as Primary. Reseller deal: Primary→Reseller company (add label "Reseller" or "Distributor"), End Customer→end-user company.
4. **Associate contacts with MEDDPICC labels by NAME** — `associations: [{targetObjectId: <contact_id>, targetObjectType: "contacts", labels: ["Champion"]}]` (or "Economic Buyer", etc.); omitting `labels` creates a basic association. Labels must already exist for the object pair (they do — see REF §10); one contact per labeled type per deal. The connector cannot read labels back, so confirm in the UI during the one-time validation run (corrections log D-11). (The old "labels are UI-only" rule is retired.)
5. **Create line item(s) linked to the product** — supply `hs_product_id` at creation plus `quantity` and, only if discounting, `discount` as a **per-unit dollar amount that YOU COMPUTED** from the rep's stated intent (% off / per-unit sale price / target deal amount-ARR-TCV-ACV) per `references/line_item_creation.md` §Discount arithmetic. **Never write the rep's raw dollar figure into `discount`** — that is the −$13.88M Infinite Campus bug (D-13). Show the computed math in the Phase-3 summary; after creating, **read back and assert `amount > 0` and `amount` matches the target** (± quantity×$0.01) before reporting success. Do **not** hand-set `hs_sku` / `class` / `product_category` / billing fields — they inherit. Read `references/line_item_creation.md` before this step; it includes the one-time validation test and the UI fallback.

**Confirm each write with a read-back** (mirrors the hygiene skill's safety gate): after each create/associate step, re-read to verify it persisted before moving on. If a step fails or partially fails, stop and report exactly what did and didn't land — never assume success.

## Phase 5 — Validate the result (before you report success)
Re-read the deal and confirm: **every line-item `amount` and the deal's `hs_tcv`/`hs_arr`/`amount` are POSITIVE and equal the rep-confirmed target** (a negative or wildly-off value means a discount was written as a total — delete/fix the line item NOW, before the rollup poisons `net_new_arr`; see D-13), `hs_tcv` is populated (line items processed), `amount` ≈ `hs_tcv`, `hs_arr` > 0 for subscription products (if $0, a billing-frequency field failed to inherit — flag it), and for New Business `hs_arr` ≈ `net_new_arr` (>5% variance → flag). **Note:** `net_new_arr` is set from the rollup by a HubSpot automation ~10s after line items land — if the line item is wrong, net-new ARR (and every pipeline report keyed on it) is wrong with it. ⚠ **Non-USD deals:** `hs_arr` is in the DEAL currency for KRW/JPY deals — compare same-currency values only; a huge "variance" on a Korea/Japan deal is usually the currency, not an error. The deal-level `products` field auto-populates from line items via a HubSpot workflow within a couple of minutes — never set it directly; tell the rep what it should show. Report only what actually persisted. If a field-level write was rejected, say exactly which field and give the rep the value to set in the UI — do not claim it's done.

## Phase 6 — Capture what went wrong (close the loop)
At the end of the run, ask once: *"Did anything about the deal or this process look wrong — a field, a value, the SKU, an owner, a step?"* If the rep flags something correctable, capture it in the **corrections-log entry format** (`D-<n> | <date> | <status> | <title>` → what was wrong → what's correct → evidence) and tell them it's logged for RevOps to add to `corrections_log.md`. Don't argue or defend a choice — the point is to catch drift early; this end-of-run capture is the loop that would have surfaced the line-item bug sooner. (If a `deal_creation_feedback` property exists in the portal, append the item there too — read current → append → write back; never overwrite. As of 2026-07-08 it does NOT exist — see corrections log D-12; do not invent it.)

## Golden rules (follow exactly)
1. **BANT is an absolute gate.** No deal without all four, ever — not on insistence, not "I'll fix it later."
2. **Confirm before every write.** Explicit phrase only; never proceed on "ok"/"sure". Show current-vs-new for any change to an existing record.
3. **Principle 0 — cite or don't claim; never fabricate.** Every value traces to a source: SKU/price/billing from the **live product record**, owner names from the **live owners object**, and dates/events/compelling-events from the **transcript or the rep** — never from training data or a plausible guess. Guessing is what produced fabricated owner names and the wrong SKU. If you can't verify it, say so and ask — don't present an inference as fact.
4. **Line items are product-linked, never field-copied.** Copying product fields onto a bare line item leaves SKU/class/category unwritable and is the documented bug this skill fixes.
5. **At least one valid line item, always.** A deal with `hs_tcv = null` is invisible to ARR forecasting — the exact defect the hygiene engine flags. No "create without line items."
6. **Append, never overwrite** MEDDPICC fields and Next Step (read current → append above/into → write back). Next Step format: `MM.DD.YY [Initials] - [action]`.
7. **Read-only means read-only.** If no write tool is loaded, produce the manual-entry checklist and stop — never a fake confirmation.
8. **Capture feedback, don't defend.** Ask at the end of every run; log corrections in the log format for RevOps. Catching errors early is the entire reason this skill carries a corrections log.

## Sanctioned writes — the ONLY objects this skill creates/edits
Create a **deal** (Sales→Discovery or Renewal→Upcoming Renewals); create/associate **contacts**; create **company associations** (Primary, End Customer, Reseller, Distributor, Paying Entity — by label name); create **contact associations with MEDDPICC labels** (Champion, Economic Buyer, Billing Contact, etc. — by label name); create **line items linked to a product**; write deal **MEDDPICC text**, **Next Step**, **deal source**, and the required scalar properties. **Everything else is out of scope** — this skill does not advance stages, close/win/lose deals, run hygiene, or compute forecasts.

## What this skill does NOT do
- **Does not create deals from unqualified leads** (forms, pricing-only, "tell me more").
- **Does not manually create custom line items** or invent SKUs/prices — Active Product Library only, with RevOps approval required for any genuine custom SKU or non-standard discount/payment term.
- **Does not overwrite** MEDDPICC/Next Step, change owners without a stated reason + current-owner display, or perform bulk operations (>1 deal) — those are out of scope here.
- **Does not compute weighted pipeline or forecasts** — pipeline questions route to `ciq-pipeline-analytics`; probabilities are known to diverge across systems (see corrections log).
